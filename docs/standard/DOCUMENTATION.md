# 文档写作规范

Rover 文档直接说明能力、规则、操作和证据。段首先给出主题，后续内容解释适用条件、步骤或依据。一段围绕一件事展开。

## 1. 按文档用途组织内容

| 文档 | 建议顺序 | 状态表达 |
|------|----------|----------|
| 实现说明 `dev/` | 能力 → 前提与接口 → 操作 → 错误处理 → 验证 → 后续工作 | 用代码和验证结果说明已实现行为 |
| 项目规划 `product/` | 目标 → 范围 → 里程碑 → 验收条件 | 区分已实现、进行中和计划 |
| 项目规范 `standard/` | 规则 → 适用条件 → 操作或示例 → 检查方式 | 必须、禁止表示约束；建议、优先表示推荐 |
| 架构决策 `product/adr/` | 背景 → 决策 → 影响与取舍 → 备选方案 → 参考 | 保留决策日期、状态和当时依据 |
| 缺陷调查 `debug/` | 日期与状态 → 现象 → 调查证据 → 修复 → 回归结果 | 区分已确认原因、待验证问题和观察结果 |

文档归属和变更同步要求见 [文档索引](../README.md)。

## 2. 直接陈述事实与操作

- 用具体对象和动词说明行为，如“导入资源”“编译依赖图”“等待 GPU 完成后映射缓冲”。
- 用参数和条件代替含糊措辞，如“验证前提：Debug 构建、显示服务和 Vulkan 验证层”。
- 删除不提供信息的“值得注意”“需要澄清”“务必牢记”等引导语。
- 用步骤表达规范；同一要求说明一次，通过链接引用其依据。
- 对比用于解释实际差异或方案取舍，避免把每项能力都写成“不是 X，而是 Y”。

例如：

| 冗余表达 | 直接表达 |
|----------|----------|
| “这不是一次性脚本，而是可维护的工具集。” | “`misc/scripts/` 按命令、构建流程和工具模块组织 Python 包。” |
| “需要澄清：图中的 Undefined 并不意味着可以丢弃旧数据。” | “图中的 Undefined 由驱动解析为实际源状态，已有内容继续保留。” |
| “切记 barrier 不能替代 GPU 完成等待。” | “导出 HostRead 后，等待 GPU 完成再映射缓冲。” |

## 3. 保留技术条件与禁止事项

范围、资源生命周期、失败行为和线程约束影响正确使用，按主题集中说明。精简措辞时保留操作含义和约束强度。

- `readback` 的格式、mip、层数和缓冲容量要求写在读回接口旁。
- CPU 读回前的等待、GPU 资源销毁顺序写在生命周期步骤中。
- 不支持的访问组合写入接口约束或能力范围；计划扩展写入后续工作。
- “禁止读取未初始化资源”“同一 pass 读写同一资源会编译失败”等具体规则继续保留。
- 同一限制在主要说明处写清，其他章节引用该说明，避免反复追加排除声明。

## 4. 让结论与证据对应

验证结果写明日期、环境、命令或测试入口，以及实际检查的行为。测试数量附带日期，或由测试运行结果查询。

清屏与像素回读验证描述为“验证清屏结果、复制和读回同步”；shader 采样、性能或其他后端的结论各自需要对应证据。性能数据保留测试条件，原因尚未确认时保留不确定性。

当前使用说明提供可重复执行的验证步骤。历史输出、环境告警和故障调查归入带日期的验证记录或 `debug/`，并从相关文档链接。

## 5. 维护示例与链接

- 代码示例使用当前 API；概念示例标明用途，避免读者把占位代码当作完整程序。
- 命令说明工作目录、构建目录和所需环境。计划中的工具标明状态后再给出预期用法。
- 仓库文件使用相对链接，链接文字说明目标内容；修改标题时同步更新锚点引用。
- 修改文档后检查本地链接、代码围栏和差异中的空白错误。
- 语言编辑保留函数名、参数、路径、返回值、需求编号和决策状态；事实更新先核对代码或已有验证记录。

## 6. 提交前检查

1. 标题和段首先说明本节内容。
2. 当前能力、历史记录和计划有明确归属。
3. 每项前提、限制或禁止事项提供实际使用信息。
4. 同一规则集中说明，重复内容改为引用。
5. 结论与证据范围一致，未知原因保持待验证状态。
6. 链接、命令和示例与对应文件及接口一致。
